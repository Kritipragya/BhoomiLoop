# Smart Dispatch Agent — Rule-based vs Agent-based

A hands-on build of an AI agent (hand-rolled ReAct pattern, no framework) for
BhoomiLoop's driver-dispatch decision — followed by a deliberate, honest
comparison against a plain deterministic rule.

Built to learn agentic AI end to end: tools, the reasoning loop, memory,
state, and guardrails — including every failure along the way, because that
is where the real understanding is.

## The headline result

| | Rule-based | Agent-based (Qwen2.5-7B, ReAct) |
|---|---|---|
| Decision | DRV001 | DRV001 (same) |
| Time | ~0.005s | ~359s |
| Speed difference | — | **~76,000x slower** |
| Cost at 500 pickups/day | ~$0 | ~$20/day (~$600/month, rough T4 estimate) |

**Both approaches reached the identical decision.** The agent added latency
and cost, not accuracy — because this dispatch decision has fixed criteria
(distance, reliability, capacity) in a fixed order, which is exactly the
profile a deterministic rule solves well.

**The real lesson: knowing when *not* to reach for an agent is as important a
skill as knowing how to build one.**

## What's inside

The notebook keeps the full build — including three failed agent attempts
with a small model before a larger one worked:

1. **Attempt 1** (Qwen2.5-1.5B) — the model hallucinated fake drivers and its
   own tool results.
2. **Attempt 2** — real drivers used, but the model skipped required tool
   calls (reasoning "laziness").
3. **Attempt 3** — a guardrail blocked a premature answer, but the small
   model still looped and eventually crashed.
4. **Attempt 4** (Qwen2.5-7B) — clean, complete, correctly-reasoned run.

Then: persisting the agent's decision to a real database (so it's actually
usable, not just printed), and the rule-vs-agent comparison above.

## The concept map

| Group | Concepts | Where |
|---|---|---|
| Reasoning pattern | ReAct loop, scratchpad, stopping condition | `run_agent` |
| Tools | Function calling, tool schema, observation | `tools.py` |
| Memory | Working memory (per task), long-term memory (history) | `messages`, `pickup_history` |
| State | Data persisted across runs | `dispatch_log`, driver `status` |
| Guardrails | Iteration limits, forced tool-use validation | `max_iterations`, tool-tracking check |

## Run it

```bash
pip install -r requirements.txt
```

Open the notebook (Colab recommended, T4 GPU). The database and tool files
(`database.py`, `tools.py`, `agent.py`, etc.) are generated by the notebook's
`%%writefile` cells as you run it — no separate setup needed.

## Note

Driver and pickup data are simulated (no real BhoomiLoop driver data exists
yet). The architecture — SQLite state, tool functions, a hand-rolled ReAct
loop — is written to be reusable once real driver data is available: swap the
simulated database for a real one and the rest of the pipeline holds.
